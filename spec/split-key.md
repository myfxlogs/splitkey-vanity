# Split-Key Vanity Address Protocol (TRON)

Version 1 — Draft

This document specifies the split-key protocol by which a buyer obtains a
vanity TRON address whose private key is **never known to the seller**.

## 1. Overview

```
Buyer (offline, local)                Seller (GPU operator)
  b  : secret scalar (32 bytes)
  B  = b·G : compressed pubkey ───────► receives B + desired pattern
                                        searches scalar i such that
                                        addr(B + i·G) matches pattern
  d  = i : offset scalar    ◄──────── returns d
  priv = (b + d) mod n
  verify addr(priv·G) matches pattern
```

`G` is the secp256k1 base point, `n` the group order.

## 2. Security properties

- **Seller learns nothing**: knowing `B`, `d`, and the final address, deriving
  `b` requires solving ECDLP. The seller's machine holds zero private-key
  material at every step.
- **Non-secret delivery**: `d` is worthless without `b`. It may be
  transmitted in plaintext; confidentiality is not required.
- **Tamper-evident order binding**: substituting `B` in transit yields an
  offset that fails verification (denial of service only — nothing can be
  stolen).
- **Objective arbitration**: any third party can verify
  `addr(B + d·G) == advertised_address` without secrets. Disputes are
  decidable by public recomputation.

## 3. Data formats

| Field | Encoding | Notes |
|---|---|---|
| `b` | 32-byte scalar, big-endian | SECRET. Generated by buyer's CSPRNG; never leaves buyer's machine except as the buyer chooses |
| `B` | 33-byte compressed secp256k1 public key, hex (66 chars) | Public. Submitted to seller with order |
| `d` | 32-byte scalar, big-endian, hex (64 chars) | Non-secret. Returned by seller |
| pattern | UTF-8 string, e.g. `suffix:55555555`, `prefix:TWsb` | Order-specified |

Validation rules:

- `1 ≤ b < n`, `1 ≤ d < n` — reject scalars out of range
- `B` MUST parse as a valid compressed secp256k1 point (prefix 0x02/0x03)

## 4. Key combination (buyer side)

```
priv = (b + d) mod n
pub  = priv·G = B + d·G      // equivalent, both may be checked
addr = TRON(pub)             // 'T' + base58check(0x41 ‖ keccak256(x‖y)[12..32])
```

The tool MUST verify `addr == advertised_address` before displaying any
private-key material.

## 5. Verification (public)

Given `(B, d)` and the advertised address, anyone can verify:

1. `Q = B + d·G` (secp256k1 point addition)
2. `addr(Q) == advertised_address`

No secret is required. This is the arbitration procedure.

## 6. Failure modes

| Case | Result |
|---|---|
| Seller returns wrong `d` | Buyer-side check `addr(priv·G)` fails → reject, dispute |
| `B` swapped in transit | Combined key derives wrong address → verification fails → no theft possible |
| Buyer loses `b` | `d` is useless; unrecoverable (buyer-side risk, disclosed) |
| Buyer submits invalid `B` | Rejected at submission (parse check) |

## 7. Privacy note

`b` MUST be generated by a cryptographically secure RNG
(`getrandom`/OS CSPRNG). The buyer tool MUST wipe `b`, `priv` and all
derived material from memory after use (`zeroize`).
